# Story 9.4: Express Server Decision

## Description

Оценить необходимость Express сервера после миграции на Supabase Storage. Принять решение: удалить сервер полностью, оставить как fallback для неавторизованных пользователей, или использовать для других целей.

## Technical Details

### Current Express Server Usage

Проанализировать `server.js`:

```javascript
// Current functionality:
// 1. File upload endpoints (POST /api/upload/font, POST /api/upload/image)
// 2. Static file serving (public/fonts/)
// 3. CORS configuration
// 4. Error handling
```

### Analysis Questions

1. **Что делает Express сервер?**
   - Обрабатывает загрузку файлов
   - Сохраняет файлы в `public/fonts/`
   - Отдает статические файлы

2. **Нужен ли он после миграции на Supabase?**
   - ✅ Supabase Storage заменяет загрузку файлов
   - ✅ Supabase Storage заменяет статическое хранилище
   - ❓ Нужен ли fallback для неавторизованных пользователей?

3. **Альтернативные варианты использования?**
   - Server-side rendering (SSR)
   - API proxy
   - Image optimization
   - Scheduled jobs

### Decision Options

#### Option 1: Remove Express Server Completely ✅ (Recommended)

**Pros:**
- Упрощение архитектуры
- Меньше кода для поддержки
- Нет необходимости в отдельном процессе
- Vite dev server достаточен для разработки

**Cons:**
- Неавторизованные пользователи не смогут загружать файлы
- Нет fallback для локальной разработки без Supabase

**Implementation:**
```bash
# Remove server files
rm server.js
rm -rf public/fonts/

# Update package.json
# Remove server scripts and dependencies

# Update .gitignore
# Remove server-related entries
```

#### Option 2: Keep as Fallback for Unauthorized Users

**Pros:**
- Неавторизованные пользователи могут загружать файлы
- Fallback для локальной разработки

**Cons:**
- Дополнительная сложность
- Нужно поддерживать два пути загрузки
- Файлы не синхронизируются между устройствами

**Implementation:**
```typescript
// In upload handlers
const userId = await getCurrentUserId()

if (userId) {
  // Upload to Supabase Storage
  await SupabaseStorageService.upload(file)
} else {
  // Fallback to Express server
  await fetch('http://localhost:3001/api/upload/font', {
    method: 'POST',
    body: formData,
  })
}
```

#### Option 3: Repurpose for Other Features

**Pros:**
- Можно использовать для SSR, API proxy, etc.
- Готовая инфраструктура

**Cons:**
- Пока нет конкретных use cases
- Преждевременная оптимизация

### Recommended Decision: Option 1 (Remove)

**Обоснование:**
1. Supabase Storage полностью заменяет функционал Express сервера
2. Неавторизованные пользователи работают через localStorage (без загрузки файлов)
3. Упрощение архитектуры — приоритет
4. При необходимости сервер можно вернуть позже

- Отключить функции загрузки файлов

- Временно поддерживать оба варианта
- Постепенно мигрировать пользователей

### Case 3: Rollback
- Если нужно вернуть Express server
- Восстановить из git history
- Обновить документацию

## Alternative Considerations

### Keep Server for Future Features

Если планируются features требующие backend:
- Server-side rendering (SSR)
- API aggregation
- Webhooks
- Scheduled jobs
- Image optimization

В этом случае:
- Переименовать в `backend/` или `api/`
- Использовать современный framework (Fastify, Hono)
- Добавить TypeScript
- Структурировать как отдельный сервис

### Use Serverless Functions

Вместо Express server использовать:
- Supabase Edge Functions
- Vercel Serverless Functions
- Cloudflare Workers
